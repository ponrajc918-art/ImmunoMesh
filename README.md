# ImmunoMesh — Adaptive Intrusion Detection and Response

### A research prototype for edge and industrial network security

ImmunoMesh is a Python-based research prototype for adaptive intrusion detection and response in edge and industrial networks. It combines synthetic traffic simulation, machine-learning-based anomaly detection, evidence generation, device trust, peer consensus, simulated quarantine and recovery, audit logging, and an interactive Streamlit dashboard.

The project also includes a real-network integration layer for packet capture, flow aggregation, device discovery, and network-device integration.

**Research scope matters:** The primary evaluation uses controlled synthetic/simulated network traffic generated and labelled by the project's own simulator. The results do not establish detection performance on real-world or industrial networks.

See [Limitations](docs/LIMITATIONS.md) and the [Threat Model](docs/THREAT_MODEL.md) before interpreting the results.

## Project Overview

ImmunoMesh explores how anomaly detection and adaptive response components can be combined in a software framework for edge and industrial network monitoring.

The research prototype is organized into ten implementation phases.

| Phase | Capability |
|---|---|
| 1 | Project configuration, logging, and CLI architecture |
| 2 | Synthetic network traffic simulation with ground-truth labels |
| 3 | Data cleaning and feature preprocessing |
| 4 | Engineering of 15 causal cybersecurity features |
| 5 | Isolation Forest anomaly detection and a frozen baseline |
| 6 | SHAP explanations and baseline-deviation evidence |
| 7 | Per-device trust evaluation |
| 8 | Simulated peer consensus |
| 9 | Adaptive response, quarantine, recovery, and SQLite audit logging |
| 10 | Streamlit dashboard, multi-seed evaluation, ablation studies, and reporting |

The repository additionally contains a real-network integration layer.

The simulation framework and real-network integration layer have different validation scopes. Simulation results provide the primary detection-performance evaluation; the loopback HIL test provides operational measurements of the real packet-capture path.

## Research Results

### Evaluation methodology

The primary evaluation uses synthetic traffic generated by ImmunoMesh's own simulator. Attack scenarios have corresponding ground-truth labels, allowing precision, recall, F1-score, and ROC-AUC to be calculated.

The reported multi-seed evaluation uses seeds **200–207**.

The following values are the reported mean results for the selected experiments.

### Headline results

| Experiment | Scenario | Precision | Recall | F1-score | ROC-AUC |
|---|---|---:|---:|---:|---:|
| E2 | Low-intensity attacks | 0.837 | 0.811 | 0.818 | 0.987 |
| E3 | High-intensity attacks | 0.948 | 0.826 | 0.877 | 0.989 |
| E4 | Five devices attacked | 0.979 | 0.747 | 0.838 | 0.986 |
| E10 | Recovery and quarantine | 0.985 | 0.818 | 0.888 | 0.991 |

These are simulation results, not measurements of detection performance on a production industrial network.

The underlying result files, generated figures, experiment tables, and run manifest are available in [`results/final/`](results/final/).

### Per-attack detection performance

Performance varies considerably by attack type.

The reported E3 per-attack recall is approximately:

| Attack type | Recall |
|---|---:|
| Port scan | 1.00 |
| Protocol irregularity | 0.98 |
| Brute force | 0.80 |
| Traffic spike | 0.67 |
| Exfiltration | 0.29 |

**Exfiltration is a major limitation of the current detector.**

The exfiltration recall estimate is based on only four of the eight seeds because an exfiltration window occurred in only those four runs. The observed per-seed recall range was approximately 0.10–0.49.

This result is reported as observed. The attack labels and reported metrics have not been adjusted to conceal the weakness.

See:

- [`results/final/RESULTS.md`](results/final/RESULTS.md)
- [`results/final/tables/per_attack_recall_E3.csv`](results/final/tables/per_attack_recall_E3.csv)
- [`docs/BRUTE_FORCE_INVESTIGATION.md`](docs/BRUTE_FORCE_INVESTIGATION.md)
- [`docs/LIMITATIONS.md`](docs/LIMITATIONS.md)

### Model comparison

The evaluation also compares Isolation Forest with One-Class SVM and Local Outlier Factor.

In the reported model-comparison experiments, **Isolation Forest is not the best-scoring detector**: One-Class SVM and Local Outlier Factor achieve higher recall, F1-score, and ROC-AUC in both reported scenarios.

Isolation Forest remains the implemented primary detector because the project also evaluates its integration with the broader evidence, trust, response, and monitoring pipeline.

The results should be interpreted alongside the model-comparison tables and the limitations of synthetic evaluation.

## System Architecture

The research workflow follows this sequence:

```text
Synthetic Traffic Simulation
            |
            v
    Data Cleaning
            |
            v
    Feature Engineering
       15 Features
            |
            v
   Isolation Forest
   Anomaly Detection
            |
            v
   Evidence Generation
   SHAP + Baseline Deviations
            |
            v
     Device Trust
            |
            v
    Peer Consensus
            |
            v
 Adaptive Response State Machine
   Quarantine and Recovery
            |
            v
   SQLite Audit Logging
            |
            v
    Streamlit Dashboard
            |
            v
 Experiment Tables and Reports
```

The real-network integration layer follows a separate operational path:

```text
Authorized Network Interface
            |
            v
      Packet Capture
            |
            v
      Flow Aggregation
            |
            v
 Device Discovery and Classification
            |
            v
 Feature Processing and Detection
            |
            v
 Live Monitoring and Dashboard
```

The two workflows must not be confused.

Peer consensus, the response state machine, and the enforcement executor are not wired into the live runtime. They operate in the simulation and are covered by unit tests using fake adapters.

## Implemented Capabilities

### 1. Synthetic traffic and attack simulation

The simulator generates network-flow data for simulated cameras, sensors, and PLC-like devices.

The implemented attack scenarios include:

- Port scanning
- Brute-force activity
- Traffic spikes
- Data exfiltration
- Protocol irregularities

The simulation includes labelled attacks and controlled variations in attack intensity and affected devices.

### 2. Feature engineering and anomaly detection

The preprocessing pipeline cleans traffic records and prepares the engineered feature matrix.

The primary detector is an Isolation Forest model trained on an anomaly-free baseline.

Its anomaly score is derived from the negative `score_samples()` output: higher scores represent more anomalous observations.

The configured decision threshold is calculated from the training anomaly-score distribution.

### 3. Evidence and explainability

ImmunoMesh combines SHAP-based explanations and baseline-deviation evidence to help interpret anomalous observations.

The evidence layer is intended to support investigation rather than establish that every flagged observation represents a confirmed attack.

### 4. Device trust and peer consensus

The trust engine maintains per-device trust information.

The simulation also models peer consensus to investigate how agreement between simulated participants affects decision-making.

These are software-model components, not evidence of validation across a distributed physical industrial network.

### 5. Adaptive response and auditing

The response state machine models quarantine, recovery, and related transitions.

SQLite audit logging records the corresponding events.

The simulation evaluates these behaviors under controlled scenarios. It does not establish that an operational switch or industrial controller was physically quarantined.

### 6. Interactive dashboard

The Streamlit dashboard provides access to the available simulation results, detection scores, evidence, trust information, response states, audit events, and experimental outputs.

The repository also includes a Live Network dashboard section for recorded real-network integration data.

The available display and data sources depend on the results included in the repository and the configured runtime.

## Installation

### Requirements

- Python 3.12 is the recommended environment for reproducing the current project setup.
- Git
- pip
- A Windows, Linux, or macOS development environment compatible with the project's dependencies

The real packet-capture and enforcement capabilities have additional operating-system and permission requirements.

### 1. Clone the repository

```bash
git clone https://github.com/ponrajc918-art/ImmunoMesh.git
cd ImmunoMesh
```

Replace the repository address if the project is published under a different GitHub URL.

### 2. Create a virtual environment

**Windows PowerShell:**

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
```

**Linux or macOS:**

```bash
python3.12 -m venv .venv
source .venv/bin/activate
```

### 3. Install dependencies

Install the development and dashboard dependencies:

```bash
python -m pip install -r requirements-dev.txt
```

The repository's `requirements.txt` is an alias of `requirements-dev.txt`.

For the smaller dependency set used by the edge runtime, see `requirements-runtime.txt`.

For reproducible experiments, consult [`docs/REPRODUCIBILITY.md`](docs/REPRODUCIBILITY.md) for the pinned dependency versions and the exact experiment commands.

## Quick Start

Run commands from the repository root.

### Run a basic simulation

```bash
python -m immunomesh.cli run
```

This runs the Phases 2–5 pipeline for one seed and reports the associated detection metrics.

### Run the full demonstration

```bash
python -m immunomesh.cli demo
```

The demonstration exercises the broader simulated workflow and writes its outputs to:

```text
results/final/demo/
```

### Launch the dashboard

```bash
python -m immunomesh.cli dashboard
```

The dashboard can also be launched directly:

```bash
python -m streamlit run immunomesh/dashboard/app.py
```

Open the local URL printed by Streamlit, normally:

```text
http://localhost:8501
```

### Run the brute-force investigation

```bash
python -m immunomesh.cli investigate
```

This runs the Phase 6 investigation of weak brute-force detection performance.

### Run the final experiment suite

```bash
python -m immunomesh.cli final
```

The final experiment suite evaluates experiments E1–E10 using multiple seeds. It supports checkpointed, resumable execution.

**This command is not required to view the existing research results.** Running it may take considerably longer than starting the dashboard.

### Regenerate the aggregate research report

```bash
python -m immunomesh.cli report
```

This aggregates the available seed results and generates the corresponding experiment tables, figures, and results report.

Regeneration may replace existing generated outputs. Review the output paths and current results before running it.

### Check real-network readiness

```bash
python -m immunomesh.cli doctor
```

The readiness check reports the availability of supported real-network capabilities. See [`docs/REAL_NETWORK_GUIDE.md`](docs/REAL_NETWORK_GUIDE.md).

## Testing and Verification

Run the automated test suite:

```bash
python -m pytest -q
```

Compile the Python package:

```bash
python -m compileall immunomesh
```

The tests cover the simulation pipeline, baseline regression, dashboard data handling, trust and mesh components, response behavior, integration adapters, security/configuration paths, and safe output handling.

Many hardware and network integration tests use mocks or fake adapters. Passing those tests does not establish physical-hardware validation.

```text

```

No warnings were reported in that run.

## Research Reproducibility

Reproducibility is a core project objective.

The repository includes:

- Seed-level result files for seeds 200–207
- A final experiment manifest
- Generated research tables and figures
- A frozen Phase 1–5 baseline
- Regression tests for the frozen baseline
- A dependency lock file
- Documentation of experiment procedures and limitations

Phases 1–5 are treated as frozen. The baseline regression test checks that the output for seed 42 does not change unexpectedly.

The final research results are generated from the project implementation and its simulated data. They should not be manually adjusted to improve headline metrics.

See [`docs/REPRODUCIBILITY.md`](docs/REPRODUCIBILITY.md) for the exact pinned versions, commands, and procedure for regenerating the reported results.

## Real-Network Integration

The repository includes an integration layer for operational network-monitoring functionality:

| Component | Implementation |
|---|---|
| Packet capture | Capture adapters, including a Linux raw-socket path |
| Flow aggregation | Flow-generation and aggregation logic |
| Device discovery | ARP, DHCP, and mDNS adapters |
| Device classification | Device identity and classification components |
| Camera integration | Camera interfaces, ONVIF, and RTSP adapters |
| Access-point integration | Access-point adapter interfaces |
| Switch integration | Dry-run, SNMP, SSH, and vendor adapter interfaces |
| Enforcement | Mode-gated executor, verification, and rollback logic |
| Live runtime | Monitoring runtime with prediction and evidence generation |
| Live dashboard | Dashboard support for recorded and available live data |

The availability of each integration depends on the operating system, permissions, hardware, configuration, and installed libraries.

### Loopback HIL validation

The project includes a loopback hardware-in-the-loop self-test using real local network traffic and the real packet-capture code path.

The recorded test is documented in:

[`results/hil/RESULTS.md`](results/hil/RESULTS.md)

It reports operational measurements such as packets captured, flows processed, dropped packets, and state transitions.

The loopback test has no ground-truth attack labels and is not used to calculate or claim real-world precision, recall, or F1-score.

### Physical hardware status

**Physical Raspberry Pi, managed-switch, and IP-camera validation has not been performed.**

The corresponding integration interfaces and hardware guides describe the intended future deployment and validation work.

The enforcement implementation has been unit-tested against fake adapters, not verified through physical isolation of an operational network device.

The real-network integration layer must therefore be regarded as an implemented software capability with limited operational validation, not a fully validated industrial deployment.

See:

- [`docs/REAL_NETWORK_GUIDE.md`](docs/REAL_NETWORK_GUIDE.md)
- [`docs/hardware/`](docs/hardware/)
- [`docs/THREAT_MODEL.md`](docs/THREAT_MODEL.md)

## Dashboard Deployment

The Streamlit dashboard can be deployed separately from the live network-monitoring runtime.

For a hosted research demonstration, Streamlit Community Cloud can deploy the repository from GitHub.

The application entry point is:

```text
immunomesh/dashboard/app.py
```

The hosted dashboard should use the saved demonstration and research results committed to the repository.

It should not be described as a remotely operating packet sensor merely because the user interface is accessible through a public URL.

Actual network capture requires an appropriately configured runtime with authorized access to the network being monitored.

## Research Limitations

The following limitations are important when evaluating ImmunoMesh.

1. **Synthetic evaluation:** The primary experiment suite uses generated and labelled synthetic network traffic. Its metrics are not measurements of real industrial-network detection performance.

2. **Uneven attack performance:** The high-intensity exfiltration recall is approximately 0.29 in the reported experiment and is based on only four of the eight seeds. Traffic-spike recall is also weaker than port-scan and protocol-irregularity recall.

3. **Detector comparison:** Isolation Forest does not outperform One-Class SVM and Local Outlier Factor on the reported recall, F1-score, and ROC-AUC comparisons.

4. **Loopback-only operational validation:** The HIL test exercises local packet capture but does not establish performance on physical industrial networks.

5. **Physical hardware:** No physical Raspberry Pi, IP camera, or managed switch has been used for project validation.

6. **Incomplete live-response integration:** Peer consensus, the response state machine, and the enforcement executor are not wired into the live runtime.

7. **Hardware adapters:** SNMP/SSH and other hardware-specific paths require appropriate devices, configurations, permissions, and further validation.

These limitations are part of the project's current scope and should remain visible in any report, demonstration, or research paper.

## Security Considerations

ImmunoMesh is a research prototype, not a production-certified security platform.

- Run real-network features only on systems and networks for which you have authorization.
- Review live-network configuration and permissions before enabling packet capture.
- Begin hardware integration in observation-only or dry-run mode.
- Do not enable enforcement against operational equipment without appropriate authorization, safeguards, and device-specific validation.
- Do not commit credentials, private keys, or sensitive network configuration to the public repository.
- Treat serialized model files as trusted artifacts only. Loading untrusted `joblib`/pickle-based files can execute arbitrary code.

See [`docs/THREAT_MODEL.md`](docs/THREAT_MODEL.md) and [`docs/hardware/security.md`](docs/hardware/security.md).

## Project Status

**Version:** `v1.0.0-research`

**Current scope:** Software research prototype with multi-seed synthetic evaluation, an interactive dashboard, automated tests, and a loopback real-packet-capture self-test.

**Future validation target:** Evaluation with physical edge hardware and representative real-world network traffic, followed by separately documented operational and detection-performance testing.
